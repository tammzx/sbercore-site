Проблема: три роли, три помощника, разрыв контекста
  • Клиент-физлицо — СберБанк Онлайн + GigaChat
  • Предприниматель — СберБизнес + Giga-ассистент
  • Сотрудник — «Пульс» + внутренние системы

История диалога не переносится при переключении роли. Согласия разрознены. Банковская тайна и ТК РФ требуют строгой изоляции.

Сценарий «разрыв»

Клиент спрашивает о вкладе в рознице, переходит в бизнес — ассистент не знает предыдущий вопрос. Клиент повторяет всё заново.

Архитектура C4 — контейнерный уровень

Границы доверия, изоляция на уровне данных, ТОЛЬКО РФ-хостинг.

Клиентские приложения → Web / Mobile / Telegram → API Gateway (FastAPI)
Operator Agent — один агент, три вариации, RBAC инструментов СберAPI
Consent Service — PostgreSQL + Redis, гранулярные согласия, отзыв ≤ 24 ч
Context Store — Redis (TTL 15 мин) + PostgreSQL + pgvector (namespace = {user_ref}:{role})
AI Core — GigaChat API (Только РФ, НУЦ Минцифры), эмбеддинги, Decimal-код-гейт
Audit Service — append-only, хеш-цепочка, хранение 5 лет
Внешние: SberID OIDC, СберБанк Онлайн, SberBusiness, HR-портал, GigaChat API

Потоки данных и согласия

Каждое обращение к ПДн предваряется проверкой согласия. Кэш Redis 60 с, источник истины — PostgreSQL.

1. SberID OIDC → JWT-сессия → псевдоним user_ref = HMAC-SHA256 (скрытой идентификации нет)
2. Диалог в роли → проверка pdn_dialogue:{role} → ответ только в namespace роли
3. Переход клиента → бизнес → согласия CROSS_RETRIEVAL_RETAIL → handoff без утечки данных
4. Вывод анклава в общий слой → CONTEXT_TRANSFER:{role}->shared → только обещлённое содержимое
5. Сотрудник → ТК РФ ст. 86 → согласие не требуется, контур изолирован

Безопасность: 152-ФЗ, банковская тайна, ТК РФ

Все требования отражены в матрице соответствия с компонентами кода.

152-ФЗ

Локализация в РФ (ст. 18), согласие (ст. 9), минимизация (ст. 5), аудит 5 лет (ст. 21).

Банковская тайна

395-1 ст. 26: ролевые анклавы, шифрование, аудит доступа, запрет доступа сотрудника к клиентским данным.

ТК РФ

ст. 86–88: сотрудник — трудовой договор, изоляция, запрет передачи ПДн коллег третьим лицам.

Команда и финальный тезис

Одна экосистема, один контекст, три роли — без выхода из контура Сбера.

Команда

  • Product Owner — бизнес-логика воронки
  • Solution Architect — архитектура и безопасность
  • ML Engineer — модели, роутер, оценка качества
  • Backend Engineer — API, согласия, аудит

Финальный тезис

Клиент находится всегда в одной удобной экосистеме Кольцевой Сбера и minimally выходит из неё, уплотняя свою жизнь и работу с банком.
